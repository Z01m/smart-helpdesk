## Исправленные ошибки

1. Один refresh-токен мог одновременно породить несколько новых: тест воспроизвёл 6 успешных ротаций. Теперь запись блокируется на время ротации/отзыва, успешен только один запрос.
2. Gateway принимал подписанный JWT без срока действия и без корректного UUID. Теперь проверяет эти поля и соответствие subject текущему аккаунту. Удалённый или пересозданный аккаунт не превращает старый токен в доступ к новому пользователю; ответ — 401.
3. AI-парсер принимал NaN; RAG мог использовать бесконечную оценку/пустой текст и возвращал отрицательную уверенность. Непригодные значения отбрасываются, отсутствие контекста означает передачу оператору. OllamaClient также отклоняет незавершённый ответ и неконечные значения embedding.
4. AI-worker сохранял результат до публикации в Kafka, а processed_event — после неё. Сбой между этими шагами мешал безопасной повторной обработке. Теперь результат, claim и result_outbox записываются атомарно; отдельный publisher повторяет сохранённое событие со стабильным идентификатором. Добавлена миграция V4__result_outbox.sql.
5. Повреждённый JSON и некорректный UUID в HTTP возвращали 500. Теперь это 400.
6. У UserService репозиторий не внедрялся через Lombok-конструктор, потому что поле не было final. Исправлено и проверено на настоящем Spring context/БД.
7. expiresIn в ответе авторизации игнорировал настройку срока JWT. Теперь возвращает настроенное значение.
8. Неограниченный X-Correlation-Id мог не помещаться в БД и содержать нежелательные символы. Принимаются только безопасные идентификаторы до 64 символов; остальные заменяются UUID, MDC очищается даже при исключении.
9. Старый интеграционный тест outbox ожидал устаревший плоский JSON. Он обновлён под действующий EventEnvelope с payload; требования приложения ради теста не ослаблялись.

## Воспроизведение

Из корня проекта, Java 21 + Maven + Docker:

```powershell
mvn clean verify
```

С установленной и запущенной Ollama и моделью qwen3:4b (или AI_MODEL):

```powershell
mvn clean verify -Plive-ai
```

Для обоих сквозных сценариев нужны также nomic-embed-text и упакованные JAR:

```powershell
mvn package -DskipTests
python scripts/e2e_local.py
```

Временные БД и Kafka не используют рабочие данные. Если Docker отсутствует, интеграционные тесты не пропускаются молча — сборка завершится ошибкой. Локальный тестовый SMTP не пересылает письма наружу. E2E удаляет только свои контейнеры/тома и останавливает только запущенные им JAR. Миграции из тестов не применялись к рабочим БД.

## Как читать тесты

`@Test` обозначает один сценарий. `@ParameterizedTest` запускает один сценарий на нескольких наборах входных данных: например, с пустой строкой, NaN и числом за границей диапазона. `assertThat` и проверки HTTP-статуса сравнивают результат с ожидаемым; несовпадение ломает сборку.

`@SpringBootTest` поднимает настоящий Spring context с сервисами и транзакциями. `@DynamicPropertySource` передаёт ему адрес временной БД. `@MockitoBean` заменяет конкретную зависимость управляемой заглушкой, чтобы воспроизвести, например, отказ AI; он не заменяет все сервисы сразу. `@EmbeddedKafka` запускает настоящий тестовый Kafka broker. Проверки через MockMvc проходят через фильтры безопасности, контроллеры и реальную бизнес-логику с тестовой БД.

Профиль live-ai использует Failsafe после упаковки. Поскольку проект не наследует Spring Boot parent, для Failsafe явно задан `classesDirectory`, как требует [документация Spring Boot](https://docs.spring.io/spring-boot/maven-plugin/integration-tests.html). JaCoCo подключён по [официальной схеме Maven](https://www.jacoco.org/jacoco/trunk/doc/maven.html).

## Что остаётся за границами проверки

Не выполнены нагрузочное/длительное soak-тестирование, независимый pentest, тестирование реального почтового провайдера и TLS-инфраструктуры production. Невозможно перебрать все тексты и ответы вероятностной модели; сквозные AI-проверки покрывают конкретные входы. Не моделировались все варианты аварий ОС, дисков, сети и многоузлового Kafka-кластера. Не весь код и не все ветки покрыты — точные значения приведены выше.

Сетевые повторы не устраняются полностью: приложение обеспечивает устойчивое хранение и идемпотентность, а клиент объединяет WebSocket-сообщения по id. SMTP может повторно доставить письмо при аварии после принятия сервером. Подробности: [security-and-delivery.md](security-and-delivery.md).
